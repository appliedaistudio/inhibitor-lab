# Inhibitor Service 1.11 Release Notes

## Overview

Release 1.11 reorganizes `inhibitor-lab` benchmark assets around a clear supported-versus-legacy lifecycle model and introduces a reproducible operational benchmark package. This is a repository benchmark, evidence, and documentation release; it does not describe a change to the Inhibitor service API or runtime behavior.

Maintained workflows now have an authoritative location under `benchmarks/supported/`, while historical implementations and outputs remain available under `benchmarks/legacy/`. The operational package combines execution, canonical evidence, deterministic reporting, and a completed reference run. Repository navigation now follows that lifecycle model.

## Highlights

### Supported benchmark structure

- Introduced `benchmarks/supported/` and the `benchmarks/supported/operational/` package as maintained execution entry points.
- Established a scalable location for future supported benchmark categories without claiming that those categories are implemented today.
- Documented execution entry points, evidence boundaries, and the distinction between benchmark lifecycle status and benchmark purpose.

### Operational benchmark package

- Added the operational benchmark notebook and `benchmark_reporting.py`.
- Added progressive burst-concurrency execution with paired Insight and Performance traffic and post-burst recovery evaluation.
- Added canonical request-level evidence and deterministic saved-run report regeneration without API calls.
- Added manifests, summary tables, charts, generated findings, and a client-facing report.
- Added a completed Inhibitor 2.24.1 reference result package.
- Added [`inhibitor_operational_scenarios.json`](../../benchmarks/supported/operational/inhibitor_operational_scenarios.json) as the version-controlled source for operational thought chains and expected
structural outcomes.
- Separated maintained scenario definitions from each run's generated `scenario_manifest.json`, preserving both reusable benchmark inputs and run-specific provenance.

### Reference-run evidence

The included Inhibitor 2.24.1 run contains one trial at configured concurrency levels 1, 20, 50, 100, and 200. Its 742 scored requests all completed successfully at the transport level, with no configured structural response anomalies. Recovery probes are separate and are not included in that scored total.

The highest per-mode successful throughput was 16.52 requests per second, tied between Insight and Performance; the highest aggregate successful stage throughput was 33.03 requests per second. Under the configured benchmark recovery rule, Performance failed with recovery latency at 2.23× its same-trial concurrency-1 baseline, while Insight completed at 0.47× its baseline.

This result is single-trial and descriptive, not production-capacity certification or statistically repeatable evidence. Each concurrency-1 recovery baseline contained one observation per mode, so the resulting ratios are diagnostic rather than statistically stable. The 2× rule is a protocol choice, not a universal service-level objective. Structural checks do not establish semantic correctness, and the result does not guarantee future behavior.

### Legacy preservation

- Moved historical operational-stress, semantic-context robustness, and drift-audit material under `benchmarks/legacy/diagnostics/`.
- Moved historical IEB versions under `benchmarks/legacy/ieb/` and retained historical assets for provenance and comparison.
- Consolidated benchmark material under `benchmarks/` and removed the competing top-level `stress_benchmarks/` taxonomy.

### Documentation

- Added benchmark lifecycle documentation and supported-versus-legacy navigation guidance.
- Documented canonical versus derived operational evidence and corrected paths affected by the restructuring.
- Updated root repository navigation and corrected the release-note filename mismatch from `2.0.md` to `1.10.md`.

## Adoption Guidance

- Start with the [benchmark lifecycle guide](../../benchmarks/README.md), then use [supported benchmarks](../../benchmarks/supported/README.md) for maintained execution.
- Use the [supported operational package](../../benchmarks/supported/operational/README.md) for operational stress and recovery evaluation, and read its guide before running the notebook.
- Treat `request_records.jsonl`, `run_manifest.json`, and `scenario_manifest.json` as the canonical regeneration inputs. Regenerate reports from saved evidence when new API calls are unnecessary.
- Use [legacy benchmarks](../../benchmarks/legacy/README.md) for historical comparison and provenance, not as the current execution path.
- Update bookmarks and external links that still reference `stress_benchmarks/`.
- Read each result package's benchmark report for run-specific findings and interpretation boundaries.
- Review [`inhibitor_operational_scenarios.json`](../../benchmarks/supported/operational/inhibitor_operational_scenarios.json) before changing benchmark coverage or expected structural outcomes.
- Treat the committed scenario file as the maintained input for new runs and each generated `scenario_manifest.json` as the immutable record of the scenario set used for that run.
- Document scenario-set changes when publishing results that will be compared with earlier reference runs.

## Looking Ahead

Potential follow-up work includes:

- adding a supported runtime-trajectory benchmark;
- increasing repeatability through additional trials;
- adding regression comparisons across Inhibitor versions;
- automating documentation-link and evidence-package validation;
- adding machine-verifiable benchmark schemas; and
- refining the taxonomy as supported categories expand.

These are prospective improvements, not capabilities included in this release.
