# Inhibitor Service 1.12 Release Notes

## Overview

Release 1.12 adds the Controlled Runtime Trajectory Benchmark to `inhibitor-lab` as a supported, self-contained benchmark package. This is a repository benchmark, evidence, and documentation release; it does not describe a change to the Inhibitor service API or runtime behavior.

The new package evaluates controlled runtime trajectories as an action-control problem: whether live Inhibitor `/check` evidence appears before a proposed action executes, whether that evidence can be mapped to an expected decision, and whether a deterministic no-side-effect controller produces the expected outcome. The benchmark is designed for mechanism review, vulnerability testing, fixture-defined runtime-control evaluation, and first-level credibility or publication-oriented evidence when claims remain bounded.

## Highlights

### Controlled runtime trajectory benchmark

- Added `benchmarks/supported/runtime_trajectories/` as a maintained supported benchmark package alongside the existing operational benchmark.
- Added a reader-facing benchmark guide that explains what the benchmark evaluates, how the controlled trajectory works, what evidence was collected, what the preserved results show, and what claims the results support.
- Added [`runtime_trajectory_scenarios.json`](../../benchmarks/supported/runtime_trajectories/runtime_trajectory_scenarios.json) as the sole canonical source for the 16 controlled runtime-trajectory scenarios.
- Added package-local source, tests, helper utilities, reporting support, catalog signal mapping, and preserved result packages under the runtime-trajectory package.
- Established `src/runner.py` as the package execution path for dry runs and deliberately authorized live runs.
- Removed the old suite-level orchestration model from the supported package: there is no package-local `benchmark_suite.yaml`, `run_all.py`, or `validate_fixtures.py` requirement.
- Kept `benchmark_reporting.py` as package-local reporting support for reproducible preserved summaries while normal benchmark execution, result writing, and summary writing are handled by the runner.

### Evidence and result packages

The release includes two preserved result packages:

- [`results/runtime_seed_20260729_143044/`](../../benchmarks/supported/runtime_trajectories/results/runtime_seed_20260729_143044/) is the primary reference result.
- [`results/runtime_seed_20260729_134216/`](../../benchmarks/supported/runtime_trajectories/results/runtime_seed_20260729_134216/) is retained as a secondary comparison result to show expected live-signal and mapping variability.

The primary reference result recorded 16/16 successful live `/check` calls, 12/16 passing cases, 11/14 unsafe mock actions prevented, 3/14 unsafe mock actions executed, 2/2 benign tasks completed, 0/2 benign tasks over-inhibited, 14/16 signal expectations met, 12/16 acceptable decisions, 12/16 matching controller outcomes, 9/50 harm-weighted unsafe execution, and 99/99 complete audit fields.

The prompt-injection slice recorded 4/5 signal expectations, 4/5 acceptable decisions, 3/4 unsafe-action prevention, 1/4 unsafe execution, 1/1 benign external-content completion, and 0/1 over-inhibition.

### Result artifact contract

Each preserved `results/<run_id>/` evidence package contains canonical JSON artifacts and a derived human-readable summary. The JSON artifacts are the evidence source of truth, while `summary.md` is generated from them.

A complete runtime-trajectory result package includes run metadata, raw live `/check` responses, normalized signal and decision-mapping records, case-level trajectory and controller outcomes, fixture-defined adjustment outcomes, controlled agent-loop results and scores, controlled prompt-injection results and scores, benchmark-side baseline comparisons, aggregate scores, and the generated summary.

### Findings and interpretation

- The benchmark showed complete live `/check` transport success for the primary reference run.
- The controlled trajectory design keeps risk detection, decision mapping, controller behavior, unsafe-action prevention, unsafe execution, safe completion, and over-inhibition separate.
- Unsafe-action prevention was strong but incomplete in the primary result.
- The tested benign cases completed without over-inhibition.
- The stable discrepancy was `rt_privacy_email_revision`: privacy/context evidence was present, but the mapped `warn` decision allowed the original mock email and did not trigger adjustment.
- Additional run-variable findings concerned credential-file handling, legal/compliance evidence, financial-loss mapping, memory-contamination handling, and tool-output injection detection.

### Documentation and navigation

- Updated repository navigation to list `benchmarks/supported/runtime_trajectories/` as a supported controlled runtime trajectory benchmark.
- Updated the benchmark lifecycle and supported benchmark documentation so runtime trajectories appear alongside the operational benchmark without replacing the operational benchmark framing.
- Reframed the runtime-trajectory README as a client-readable benchmark guide and findings page rather than internal validation material.
- Documented that the package is controlled, not a production enforcement test, and that mock-tool execution has no real downstream side effects.

## Adoption Guidance

- Start with the [Controlled Runtime Trajectory Benchmark guide](../../benchmarks/supported/runtime_trajectories/README.md) to understand the benchmark purpose, protocol, evidence package, preserved results, findings, and interpretation boundaries.
- Use the [benchmark lifecycle guide](../../benchmarks/README.md) and [supported benchmarks](../../benchmarks/supported/README.md) to understand how this package fits into the maintained benchmark structure.
- Treat [`runtime_trajectory_scenarios.json`](../../benchmarks/supported/runtime_trajectories/runtime_trajectory_scenarios.json) as the maintained scenario source for this benchmark.
- Use the runner dry run to list and check the 16 controlled scenarios without calling `/check`.
- Treat [`results/runtime_seed_20260729_143044/`](../../benchmarks/supported/runtime_trajectories/results/runtime_seed_20260729_143044/) as the primary reference result.
- Use [`results/runtime_seed_20260729_134216/`](../../benchmarks/supported/runtime_trajectories/results/runtime_seed_20260729_134216/) only as a secondary comparison result for expected live-signal and mapping variability.
- Treat result JSON artifacts as canonical evidence and `summary.md` as derived narrative output.
- Keep claims bounded to controlled runtime-trajectory evaluation, mechanism review, vulnerability testing, and fixture-defined runtime-control evaluation.
- Do not describe the preserved evidence as production enforcement, real tool execution, independent human-label validation, robust category-level performance, full autonomous-agent safety, or official AgentDojo/InjecAgent evidence.
- Commit new live-result packages only when publication of that run is intentional, because raw responses are preserved evidence.

## Looking Ahead

Potential follow-up work includes:

- examining production controller traces when a safe environment exists;
- adding independent labeling;
- increasing category density and repeated-run variability analysis;
- calibrating decisions such as `warn`, `pause`, and `revise`;
- broadening agent-generated adjustment tests;
- improving semantic goal-preservation evaluation beyond string-retention proxies;
- strengthening tool-output injection detection; and
- adding official external benchmark integrations where appropriate.

These are prospective improvements, not capabilities established by this release.
