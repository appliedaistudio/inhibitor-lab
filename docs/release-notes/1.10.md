# Inhibitor Service 1.10 Release Notes

## Overview

Version 1.10 turns inhibitor-lab’s API reference into a deployment-oriented commercial integration guide. This release rewrites `docs/inhibitor-api.md` from a compact endpoint reference into a fuller document that explains why to use Inhibitor, how to insert it into existing agent and application flows, how to choose between `text` and `thought_chain`, and how to operate the service safely in production.

The result is a more onboarding-friendly and production-useful source of truth for teams moving from experimentation to real integrations, especially where auditability, observability, runtime gating, and governance all need to stay aligned.

## Highlights

- Reframed the API documentation around a commercial integration model, positioning Inhibitor as a pre-send safety gate, compliance checkpoint, runtime monitor, logging and review layer, mitigation signal provider, and context-aware evaluator for multi-turn systems.
- Expanded `/check` guidance into a clearer integration guide with distinct single-message and thought-chain evaluation paths, explicit request-body field documentation, mode-selection guidance, and examples showing why context can materially change a safety verdict.
- Strengthened security and deployment guidance around authentication, backend or edge integration boundaries, production base URL usage, and CI retrieval of the public OpenAPI schema so generated clients and contract checks stay aligned with the live service.
- Added substantially richer code examples in cURL, Python, and JavaScript / Node.js, including both direct checks and production-style gating patterns that teams can adapt into real request paths.
- Added context-aware agent safety gate examples in both Python and JavaScript so teams have clearer insertion points for evaluating candidate responses against recent interaction history rather than in isolation.
- Brought `/logs` and `DELETE /logs/{id}` into the same operational frame as `/check`, positioning log retrieval and cleanup as part of observability, debugging, internal review, compliance workflows, and test-data hygiene.
- Added concrete use-case demonstrations for customer support agents, compliance review workflows, autonomous agent loops, enterprise deployment gates, and context-sensitive safety checks.
- Added a production-readiness checklist, recommended application decision mapping, error-handling guidance, and best practices so teams can make explicit choices about fail-safe behavior, escalation, monitoring, and governance handling.

## Adoption Guidance

- Start with `../inhibitor-api.md` as the primary integration reference when wiring the Inhibitor into a product, backend workflow, or agent loop.
- Use `../../notebooks/quickstart_inhibitor.ipynb` alongside this release so the prose reference and a live notebook path stay aligned while teams validate credentials, `/check`, `/logs`, and OpenAPI retrieval.
- Default to `performance` mode for latency-sensitive production gates, but keep `insight` mode in the loop for audits, incident reviews, debugging, and policy-tuning workflows.
- Prefer `thought_chain` over single-message checks whenever the safety decision depends on prior user intent, agent behavior, or escalation context.
- Pull the public OpenAPI schema into CI and pair it with lightweight health and smoke checks so contract drift is caught before deployment rather than during runtime incidents.
- Treat `/logs` usage as operational infrastructure, not just debugging convenience: it supports review, dashboards, audit workflows, and post-incident analysis.

## Looking Ahead

- Keep the API reference synchronized with the newer structured response envelopes already surfacing in the notebooks so example payloads, parsing guidance, and release notes do not drift.
- Surface this richer API guide more prominently from the root README and onboarding paths so commercial and enterprise evaluators can find the integration story faster.
- Add more scenario-specific examples for common regulated or high-risk deployment patterns where context-aware checks, escalation, and review records all matter together.
- Consider pairing the documentation with lightweight SDK wrappers or maintained middleware snippets so teams can adopt the recommended patterns with less copy-paste adaptation.
